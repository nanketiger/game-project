# 软件工程化说明文档

## 1. 概述

本文档描述"平台冒险游戏（肉鸽闯关·demo版）"项目所采用的软件工程化手段，涵盖自动化、协作化、过程管理三大方面。项目由四人小组协作开发，按规范化流程组织开发活动。

---

## 2. 版本控制

### 2.1 工具与平台

- **版本控制系统**：Git
- **远程仓库**：GitHub（见 `git remote` 配置）
- **分支策略**：单分支开发（main），未设置 develop/feature 等多分支模型

### 2.2 提交规范

采用 **Conventional Commits** 规范，提交信息格式为 `<type>: <description>`：

| 类型 | 说明 | 示例 |
|------|------|------|
| `feat:` | 新功能 | `feat: 增加角色粒子特效和人物待机光环` |
| `fix:` | 缺陷修复 | `fix: 合并远程分支的炸弹/Boss特效` |
| `refactor:` | 重构 | `refactor: 提取 Monster 类状态机` |
| `chore:` | 杂项/工程化 | `chore: 将 Particle FX 文件夹移出 git 跟踪` |

最近的提交记录示例：
```
08b07ca 数值修改+重启芯片特效
a110276 增加了人物待机特效，更改5-10关的地图
e26337d fix: 合并远程分支的炸弹/Boss特效 + 本地的粒子特效和人物跟随效果
cf9bd4e 角色+地图的粒子效果
5bf35ee chore: 将 Particle FX 文件夹移出 git 跟踪，由 .gitignore 接管
```

### 2.3 版本忽略策略

`.gitignore` 配置：

```
craftpix-net-507107-free-soldier-sprite-sheets-pixel-art/Soldier_1/
craftpix-net-507107-free-soldier-sprite-sheets-pixel-art/Soldier_3/
Particle FX 1.3 Free/
```

- **未使用的素材目录**排除在外，减小仓库体积
- **第三方粒子特效素材**排除（仅使用部分导出帧）

## 4. 测试管理

### 4.1 测试策略

| 维度 | 说明 |
|------|------|
| **测试类型** | 功能测试（手工）、边界测试、回归测试 |
| **测试环境** | Windows 11，Chrome/Edge 浏览器，1920×1080 |
| **运行方式** | `file://` 协议直接打开 `index.html` |

### 4.2 测试用例覆盖（7 模块 / 19 用例）

| 模块 | 用例数 | 覆盖内容 |
|------|--------|----------|
| 角色控制 | 3 | 移动（A/D）、跳跃（K）、边界约束 |
| 战斗系统 | 4 | 水平射击、8方向射击、命中判定、怪物死亡 |
| 关卡系统 | 4 | 关卡生成、怪物全灭→传送门、传送门碰撞、通关 |
| 传送门 | 2 | 视觉表现（帧动画）、位置 |
| 遗物系统 | 2 | 遗物选择、范围扩大效果 |
| 背包系统 | 2 | 打开背包、拾取掉落物 |
| 暂停与音量 | 2 | 暂停/恢复、BGM 音量滑块 |

### 4.3 缺陷跟踪

缺陷跟踪采用表格管理，记录每条缺陷的完整生命周期：

| 字段 | 说明 |
|------|------|
| ID | 唯一编号（#1 ~ #7） |
| 描述 | 问题现象 |
| 模块 | 归属模块 |
| 严重度 | 阻塞 / 高 / 中 / 低 |
| 状态 | 全部 7 个已关闭 |
| 修复方式 | 具体修复手段 |

**典型缺陷案例**：

- **#1（阻塞）**：PixiJS v8 CDN 被浏览器 Tracking Prevention 拦截 → 放弃 PixiJS，改用纯 CSS + PNG 帧序列方案
- **#3（阻塞）**：传送门清理逻辑导致后续传送门不再出现 → 移除全量 canvas 删除，改为精确 DOM 清理
- **#6（中）**：传送门碰撞检测不准确 → 使用固定宽高手动计算 AABB 碰撞区域

## 5. 自动化程度

### 5.1 当前状态

项目为纯前端静态页面（HTML + CSS + JS），**无构建步骤**，因此：

- 无 **CI/CD 流水线**
- 无 **自动化测试**
- 无 **代码质量检查**（ESLint/Prettier）
- 无 **打包/压缩**（Webpack/Vite）

这些选择是基于项目规模的有意取舍——零依赖意味着任何人可以通过浏览器直接打开运行，无需安装 Node.js 或配置构建环境。

### 5.2 已实现的自动化

| 机制 | 说明 |
|------|------|
| **资源预加载** | `index.html` 内嵌资源扫描逻辑，自动收集 CSS 中引用的图片并逐张预加载，显示进度条 |
| **BGM 音量持久化** | 使用 `localStorage` 自动存储/恢复音量设置 |
| **游戏循环** | `requestAnimationFrame` 驱动，无需手动管理定时器 |

## 6. 协作化

### 6.1 协作方式

- **团队规模**：四人小组
- **协作模式**：通过 Git + GitHub 进行分支合并（如 `fix: 合并远程分支的炸弹/Boss特效 + 本地的粒子特效和人物跟随效果` 提交所示）
- **代码评审**：通过 Git 分支合并进行代码集成，未设置正式的 PR Review 流程
- **任务管理**：通过 Git 提交信息跟踪进度（未使用 GitHub Issues 或 Project）

### 6.2 代码组织约定

| 约定 | 说明 |
|------|------|
| **文件命名** | JS 文件使用 camelCase（`portalEffect.js`、`playerEffect.js`） |
| **类命名** | PascalCase（`Monster`、`Bomb`、`PortalEffect`、`PlayerEffect`、`IdleAura`、`ReviveEffect`） |
| **函数命名** | camelCase（`damagePlayer`、`spawnDrop`、`refreshMap`），语义化命名 |
| **常量命名** | UPPER_SNAKE_CASE（`MAX_LEVEL`、`MONSTER_CONFIG`、`RELICS`） |
| **注释风格** | 使用分隔注释标记代码段落（`// ========== 段落名 ==========`） |
| **文件分隔** | 每个独立功能一个 JS 文件（怪物系统、遗物系统、背包系统、各类特效） |

### 6.3 知识传递

- **内联文档**：关键业务逻辑带有注释（如状态机切换、碰撞检测缩框原因）
- **独立文档**：架构设计、运维、测试文档覆盖核心工程活动
- **命名可读性**：变量名和函数名即文档，尽量减少注释的需要

## 7. 过程管理

### 7.1 开发生命周期

```
需求分析 → 架构设计 → 编码实现 → 手工测试 → 缺陷修复 → 文档沉淀
```

实际提交历史反映了迭代式开发过程：
1. 基础功能（角色、地图、怪物）
2. 特效增强（粒子效果、人物跟随、待机光环）
3. 数值调整 + 功能补齐（重启芯片、Boss 特效）
4. 工程化收尾（`.gitignore` 整理、文档编写）

### 7.2 过程改进建议

| 方面 | 当前状态 | 改进方向 |
|------|----------|----------|
| 分支管理 | 单分支 | 引入 feature/bugfix 分支，PR 合并 |
| 任务追踪 | 无 | 使用 GitHub Issues 或 Projects 看板 |
| 自动化测试 | 无 | 关键路径（战斗、关卡切换）引入 Cypress E2E |
| 代码规范 | 约定俗成 | 添加 ESLint + Prettier，pre-commit hook 自动格式化 |
| 持续集成 | 无 | GitHub Actions 静态检查 |
| 发布管理 | 无 | 使用 Git Tag 标记版本 |

## 8. 总结

本项目作为游戏 Demo，在有限的人力投入下实践了以下软件工程化手段：

1. **版本控制**：Git + Conventional Commits + .gitignore 管理
2. **文档体系**：架构设计、运维、测试计划/用例/缺陷/质量报告全覆盖
3. **测试管理**：7 模块 19 个手工测试用例 + 7 个缺陷的完整跟踪记录
4. **代码组织**：模块化文件拆分、语义化命名、注释分段、配置表驱动

尚未引入但适宜未来加强的方面：自动化测试、CI/CD 流水线、代码静态分析、版本标记与发布流程。
